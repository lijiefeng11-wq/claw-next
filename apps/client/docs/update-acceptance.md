# 检查更新：真实 Mac 验收清单

用途：用户安排在真实 Mac 上验收“检查更新”时，照本清单逐项执行并留证据。

- 清单本身不是验收。在用户 Mac 上实际执行并留下证据之前，不能说“已在真实 Mac 上验证自动更新”。
- 代码、虚构夹具测试和 CI 通过，只说明实现与模拟场景成立，不代替这里的实测。
- 只在用户直接安排时执行。替换、重启、诊断客户端都属于“需要用户直接安排”的操作。

功能说明见 [README 的“检查更新”](../README.md#检查更新mac-打包版)。

## 0. 安全边界（每次执行前确认）

- [ ] 不碰后台 launchd 任务 `com.claw-next.backend.receive-only` 及其数据。执行前后各记一次它的 PID（`launchctl print gui/$(id -u)/com.claw-next.backend.receive-only | grep pid`），两次应相同。
- [ ] 不碰旧仓库目录 `~/-pdd-Claw-Next`。
- [ ] 正式店铺全部处于“仅观察”或“人工接管”。更新期间本来就会暂停领取和发送，这一项是额外保险：验收中出现意外时，不会有自动发送。
- [ ] 在“应用程序”文件夹之外另留一份能启动的旧版本副本，作为本清单之外的兜底，例如已有的 `~/Claw-Next-Client-旧版备份.app`。
- [ ] 证据里不放口令、Cookie、买家昵称或聊天内容。截图只截“客户端设置”区域，日志只摘 `update ` 开头的行。

## 1. 前置条件

- [ ] **本机装的是 CI 发布的版本。** 本机打包或开发运行的版本没有构建信息，不提供检查更新。第一次需要手动装一个 CI 发布的版本 N，这一步本身也是替换客户端，需要用户安排：
  1. 从 Releases 下载 `client-N-<完整SHA>` 的 zip 与 `.sha256`。
  2. 核对来源（见第 2 节）。
  3. 解压后放进“应用程序”，替换原客户端。
- [ ] 有一个更新的候选版本 M：M > N，且 M 的提交是 N 的后续。main 每次推送且检查全过后会自动发布一个。
- [ ] “客户端设置”显示“当前版本：构建 N（7 位 SHA）”，并有“检查更新”按钮。

## 2. 构建来源核对（安装 M 之前）

发布页上的 `.sha256` 与 zip 同源，只能证明完整性。来源靠下面几项一起核对：

| 核对项 | 方法 | 期望 |
| --- | --- | --- |
| tag 与提交 | `gh api repos/lijiefeng11-wq/claw-next/git/ref/tags/client-M-<SHA>` | 指向同一个完整 SHA |
| release 状态 | `gh api repos/lijiefeng11-wq/claw-next/releases/tags/client-M-<SHA>` | 非草稿、预发布，资产恰好两个：`Claw-Next-Client-darwin-arm64.zip` 和同名 `.sha256` |
| 产生它的 CI | Actions 中 run_number 为 M 的那次运行 | 是 main 的 push 运行，`head_sha` 等于该 SHA，所有 job 成功，Publish job 成功 |
| 与 CI 产物一致 | 用 REST 接口下载该运行的 `Claw-Next-Client-macOS` 产物，与 release 的 zip 分别 `shasum -a 256` | 两个哈希一致，且等于 `.sha256` 里的值 |
| 包内构建信息 | 解压 zip，读 `Claw-Next-Client.app/Contents/Resources/build-info.json` | `{sha: 该SHA, run: M, platform: "darwin", arch: "arm64"}` |

证据：上面每一项的命令输出（完整 SHA、run id、两个哈希）。

## 3. 场景与通过标准

每个场景都要记下：开始和结束时间；操作前后的“客户端设置”截图；客户端日志 `~/Library/Application Support/Claw-Next-Client/logs/client-<日期>.log` 中 `update ` 开头的行；暂存目录 `/Applications/.Claw-Next-Client.update-*/swap.log` 的全文；`~/Library/Application Support/Claw-Next-Client/update/ready.json`；后台任务 PID 前后对比。

### 3.1 正常更新：未开启“崩溃后自动重启”

1. 点“检查更新”，应显示“发现新版本：构建 M”。
2. 点“下载并安装”，确认弹窗。
3. 依次看到下载、等待任务结束、正在安装；客户端自动退出，约 1–2 分钟内自动重新打开。
4. 如果 macOS 弹出提示，按提示允许，并记下提示的原文与截图。

通过标准：
- [ ] 新打开的客户端显示“当前版本：构建 M”。
- [ ] `swap.log` 依次为 `start` → `agent=0` → `moved_old` → `moved_new` → `done`。
- [ ] `ready.json` 中的 `run` 等于 M。
- [ ] 暂存目录里有 `previous.app`，即构建 N 的完整副本。
- [ ] 店铺按退出前的样子恢复，运行模式不变。
- [ ] 后台任务 PID 不变。

### 3.2 正常更新：开启“崩溃后自动重启”（托管启动）

前提：开启崩溃重启，并让客户端处于托管运行，即交接完成后由系统任务启动。另需一个比当前更新的候选版本。

通过标准：
- [ ] 同 3.1，但 `swap.log` 中为 `agent=1`。
- [ ] 更新后 `launchctl print gui/$(id -u)/com.claw-next.client` 显示 `state = running`，程序路径仍是 `/Applications/Claw-Next-Client.app/...`。
- [ ] 后台任务 PID 不变；只有 `com.claw-next.client` 被卸载并重新加载过。

### 3.3 已是最新、不会回退

1. 更新完成后再点“检查更新”。

通过标准：
- [ ] 显示“已是最新版本”。不会提供旧版本，也不会重复提供同一版本。

### 3.4 更新期间暂停自动处理（只在“仅观察”下看）

1. 店铺保持“仅观察”。
2. 在“等待进行中的任务结束”或“正在安装”期间，让买家消息进来（自然到达即可，不主动制造）。

通过标准：
- [ ] 这段时间到达的消息，记录里的原因是“客户端正在安装更新，暂停发送”。
- [ ] 没有任何平台发送、附加发送或标星。
- [ ] 已有的 unknown 记录保持原样。

### 3.5 下载中断

1. 点“下载并安装”后，在下载阶段断开网络（关 Wi-Fi 或拔网线）。

通过标准：
- [ ] 显示“更新未完成：……现有客户端未改动”。原因可能是网络错误代码（如 `ENOTFOUND`、`ECONNRESET`）、下载超时、下载中断或校验值不一致。
- [ ] 客户端没有退出，版本不变。
- [ ] 本次暂存目录已删除，“应用程序”里没有残留的半成品。
- [ ] 恢复网络后可以重新检查、重新安装。

### 3.6 新版本打不开时自动回滚（视情况）

真实环境里难以安全地造出“打不开的新版本”：CI 只发布测试通过的包，不能为验收发布坏包。只在下面这种自然情况下记录：macOS 拦截了新版本，用户在提示里选择不打开或取消。

通过标准：
- [ ] 约 2 分钟后，`swap.log` 出现 `not_ready` → `rolled_back`。
- [ ] 旧版本 N 自动重新打开，显示“构建 N”。
- [ ] 新版本留在暂存目录的 `failed.app`。

没出现这种情况时，本项以虚构夹具的结果为准（`test/update.test.ts` 的“替换脚本”各用例），记录为“真实环境未覆盖”。

### 3.7 客户端没有按时退出、权限不足

真实环境里难以安全构造，以虚构夹具的结果为准（`test/updater.test.ts`、`test/update.test.ts`），记录为“真实环境未覆盖”。

## 5. 清理

- 每次安装前，客户端只自动清理已结束的暂存目录：已回滚的、改动前就中止的，以及较早的成功目录。保留最近一次成功的目录，里面的 `previous.app` 可用于手动回退。
- 回滚失败（`rollback_failed`）或状态不明的目录一律保留，需人工查看。
- 想手动删除暂存目录时，先确认客户端已退出、`swap.log` 最后一行是 `done` 或 `rolled_back`。

## 6. Windows

Windows 目前没有自动更新，只能手动替换，本清单不适用。如果以后要做，单独设计和审查，大致方向是：
- 复用同一套发布与核对规则：CI 产物、完整 SHA、运行序号、每一跳地址核对、解压前核对条目。
- 替换由随应用附带的守护程序（`supervisor.js`）在客户端退出后完成，同样先等进程退出、认领后再改名，失败就保留旧版本。
- 未签名的应用会被 SmartScreen 提示，处理方式同 Mac：不绕过，只提示用户。

以上只是方向，没有实现，也没有测试。
