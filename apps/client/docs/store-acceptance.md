# 正式店铺逐店验收与多店持续运行（前台部分）

用途：用户安排正式店铺接入时，前台按本方案逐店推进、留证据。

- 方案本身不是验收。没有在正式店铺上实际执行并留下证据之前，不说“某店已可自动回复”。
- 自动测试、模拟平台、虚构页面的结果只说明实现与模拟场景成立。
- 后台判断质量（回复是否合适）由后台另行验收，不在本文范围。
- 每一阶段的推进（包括切到“自动处理”）都须用户直接安排。

## 0. 安全边界（每店每阶段开始前确认）

- [ ] **同一店铺只能有一个自动发送者。**
  - 切到“自动处理”前，由用户核对该店没有其他自动回复工具在发送，例如旧 Claw、平台自带的自动回复或其他第三方工具。
  - 客户端只能保证本项目内同店只有一个持有发送归属的实例（另一实例会显示“发送归属被占”），管不到项目之外的工具。
- [ ] 不碰后台 launchd 任务 `com.claw-next.backend.receive-only` 及其数据，不碰旧仓库目录 `~/-pdd-Claw-Next`。
- [ ] 新店默认“仅观察”，按阶段逐级放开，不跳级。
- [ ] 证据只用计数、时间、原因代码和截图里的状态区域，不收集买家昵称、聊天正文、订单号或口令。
- [ ] **出现以下任一情况立即停止**：该店切回“仅观察”，保留现场日志，报告用户，不自行恢复。
  - 发错店：A 店的回复从 B 店发出，或发给不是触发它的买家。
  - 同一条买家消息被发送两次。
  - unknown 被重发。
  - 在“仅观察”或“人工接管”下发生了发送。

## 1. 逐店验收：分阶段推进

每店独立推进；一店的阶段结论不代表其他店。

### 阶段 A：接入与身份

1. 添加店铺，填写后台地址、店铺口令和平台店铺编号；打开本店工作台，扫码登录。
2. 核对：

| 检查 | 期望 | 证据 |
| --- | --- | --- |
| 后台连接 | `/api/v1/me` 的 `shop_id` 与本店配置一致；用别店口令时显示“口令属于其他店铺”并拒绝 | 状态标签截图 |
| 平台身份 | `/chats/userinfo/realtime` 与 `queryCustomServiceInfo` 两处店铺编号一致，且等于配置值；状态为“已核验” | 状态标签截图 |
| 发送归属 | 本店持有发送归属；另一实例或另一台电脑连同一店时显示“发送归属被占” | 状态标签截图 |
| 串店防护 | 在本店工作台登录成别的店时，提示疑似串店并停止；重新登录本店后恢复 | 截图（可选，只在用户方便时做） |

### 阶段 B：仅观察（建议至少 1 个营业日）

只收消息、拿建议回复，不发送。核对接收是否可靠：

| 指标 | 怎么核对 | 通过标准 |
| --- | --- | --- |
| 漏收 | 选 2–3 个时段，各约 30 分钟，用平台未读或会话列表与客户端记录逐条对照计数 | 漏收 0；若有，记下时间和原因代码 |
| 重复 | 客户端记录中同一条平台消息是否出现两次 | 0 |
| 错店 | 记录里是否出现不属于本店的会话 | 0 |
| 发现延迟 | 日志 `timing_summary` 各段耗时，不含正文 | 记录中位数与最大值，仅供参考，不设硬门槛 |
| 历史完整 | 记录中 `history_complete=false` 的比例与原因 | 记录比例；不完整时后台按规则转人工，不算失败 |
| 页面健康 | 掉线、崩溃、登录失效提醒的次数与恢复情况 | 每次都有提醒；能自动恢复的已恢复 |

### 阶段 C：有人值守的自动处理（短时间、小范围）

前提：阶段 B 通过；用户直接安排一个有人在场的时段（建议 1–2 小时）。

1. 该店切到“自动处理”；值守人员同时看着平台聊天页。
2. 每条自动发送都核对：

| 检查 | 期望 |
| --- | --- |
| 回执 `sent` | 有平台消息编号；平台聊天里确有这条客服消息，买家和店铺都对 |
| 回执 `not_sent` | 平台聊天里确实没有这条 |
| 回执 `unknown` | 不重发；界面显示“结果待核查”；人工到平台核对后在验收记录里写结论（客户端不会改 unknown） |
| 20 秒时限 | 超时的显示“本条待人工”，不再发送 |
| 人工接管 | 在客户端对某个会话点“人工接管”后，该会话不再自动发送；值守人员直接在平台手动回复时，客户端看到这条客服消息后，基于旧上下文、还没点击的自动回复按“已有更新消息或上下文已变化，旧判断失效”放弃（已经点击的不受影响） |
| 附加发送 | 只在能力已确认时出现；每次核对候选名称与平台实际发出的一致 |

通过标准：错店 0、重复发送 0、unknown 被重发 0；`sent` 抽查全部与平台一致；`not_sent` 抽查平台确实没有。

### 阶段 D：持续自动

前提：阶段 C 通过；用户直接安排正式开启。

每日检查（约 5 分钟）：
- `unknown_stats` 的数量与原因，逐条在平台核查结论。
- 页面掉线、崩溃、登录失效的提醒次数。
- 后台不可用的时长。
- 有无“发送归属被占”“疑似串店”。

出现第 0 节的停止条件，按停止流程处理。

## 2. 多店持续运行

多店同时运行时，前台须保证：
- 每店有独立的数据目录、平台会话分区（`persist:claw-next-shop-<shop_id>`）、运行时和发送归属；
- 界面切店只换显示，不停后台店铺；
- 一店的故障不影响另一店。

| 场景 | 期望 | 自动测试现状 |
| --- | --- | --- |
| 两店同时收消息、同时自动回复 | 各自只在本店平台发送，记录与后台事件各归各店 | 已有：`runtime.test.ts`“两店数据、凭据、会话互相隔离” |
| A 店配置用了 B 店口令 | 拒绝，不提交 | 已有：“串店凭据被拒绝” |
| 平台登录成别的店 | 不提交、不发送，提示疑似串店 | 已有：runtime 与界面端到端 |
| 同店第二个实例 | 后者“发送归属被占”，不提交 | 已有：“另一实例争抢同店发送归属” |
| 界面切店、缩放、并行点击 | 不影响后台店铺页面与点击 | 已有：`scripts/test-platform-workspace.cjs`（Mac 合成页面） |
| A 店登录失效、B 店正在收发 | B 店照常收发，A 店不提交、不发送 | `test/multiShop.test.ts`（#49）；页面崩溃的恢复见 `pddPageHealth.test.ts`（单店） |
| 两店出现相同的买家会话编号 | A 店的回复只进 A 店，B 店不受影响 | `test/multiShop.test.ts`（#49） |
| A 店出现 unknown | 只锁定 A 店该条事件；B 店与 A 店其他买家照常 | `test/multiShop.test.ts`（#49） |
| 断开 A 店（不是退出客户端） | B 店进行中的发送与回执不受影响 | `test/multiShop.test.ts`（#49） |
| 重启恢复 | 两店分别按退出前的打开状态与各自运行模式恢复 | 已有：`sessionStore.test.ts`“不同店铺并行恢复”“另一家店的操作互不影响”等；运行模式取自各店配置，恢复时不改 |

以上自动测试只覆盖模拟平台；正式店铺上的多店表现仍须在阶段 B–D 中观察记录。

正式运行时的长时间观察项（阶段 D 期间记录，不设硬门槛，用于发现问题）：
- 连续运行 24 小时后客户端内存占用的变化；
- 日志大小（单文件超过 20 MB 会停写并留提示）；
- 电脑睡眠唤醒后各店是否恢复收发；
- 网络断开再恢复后各店的恢复时间。
